# Selenium Page-Object Fixture Framework

[![Selenium Test CI](https://github.com/azzipmp/selenim-Pagefactory-fraework/actions/workflows/ci.yml/badge.svg)](https://github.com/azzipmp/selenim-Pagefactory-fraework/actions/workflows/ci.yml)

A Selenium + Java framework using TestNG, Page Object Model, CSV test data,
Rest Assured API tests, and Extent reporting.

## Why this mirrors Playwright

| Playwright (JS/TS) | This framework (Java + TestNG) |
|---|---|
| `test('...', async ({ page }) => {...})` | `@Test public void testMethod() {...}` |
| Test framework injects `page`, `browser`, `context` | Lifecycle setup/teardown is handled with TestNG annotations |
| Fixture scope handles setup/teardown automatically | `DriverFactory` manages browser lifecycle |
| Fixtures are composable — request only what you need | Page objects are created as needed in test flow |

The framework keeps setup logic centralized and supports environment-based
config switching (`qa`/`uat`) through Maven parameters.

## Architecture

```
src/main/java/
├── framework/
│   ├── DriverFactory.java        # ThreadLocal WebDriver lifecycle (parallel-safe)
│   ├── BasePage.java              # Common PageFactory + wait setup for every page
│   └── PageObjectExtension.java   # The "fixture provider" — the core of this design
└── pages/
    ├── LoginPage.java
    └── HomePage.java

src/test/java/
└── tests/
    └── LoginTest.java             # Zero manual instantiation in test bodies
```

### How setup works, step by step

1. `@BeforeTest` reads browser config and initializes `WebDriver` via `DriverFactory`.
2. Test methods use the same driver to execute page-object flows.
3. CSV test data is loaded through `CsvUtils`.
4. `@AfterTest` closes the driver with `DriverFactory.quitDriver()`.

## Login Reliability: Retries And Locator Fallbacks

The smoke login test uses TestNG's `RetryAnalyzer`:

```java
@Test(groups = {"smoke"}, retryAnalyzer = RetryAnalyzer.class)
public void validLoginNavigatesToHomePage() {
    // test flow
}
```

`tests.listeners.RetryAnalyzer` allows two retries after the initial failure,
so a failed test can run up to three times in total:

1. Initial attempt
2. Retry 1
3. Retry 2

Before each retry, the current WebDriver session is closed. The test then
obtains a fresh driver through `DriverFactory`. Retries are intended for
transient browser or network failures and should not be used to hide a
consistent application defect. A successful test is not retried.

The login page also provides lightweight fallback locator handling through
Selenium's `@FindAll` annotation. Each login control has more than one locator:

| Control | Fallback locators |
|---|---|
| Username | `id=username123`, `name=username` |
| Password | `id=password`, `name=password` |
| Login button | `id=submit`, `button[type='submit']` |

For example:

```java
@FindAll({
    @FindBy(id = "username123"),
    @FindBy(name = "username")
})
private WebElement usernameInput;
```

Selenium tries the configured alternatives when resolving the element. This
is a controlled fallback mechanism, not a full AI self-healing system: it does
not discover new locators or modify the test automatically. Keep the fallback
locators aligned with stable application attributes such as `name`, `id`, or
`data-testid`.

## Environment Switching

Use Maven parameters to switch environments without code changes:

```bash
mvn test -Denv=qa
mvn test -Denv=uat
```

You can also override URL directly:

```bash
mvn test -Denv=uat -Duat.url=https://example-uat-url
```

## Running

```bash
mvn test
mvn test -Dheadless=true   # run headless
mvn test -Denv=qa          # run with QA config values
mvn test -Denv=uat         # run with UAT config values
```

Environment resolution order for a key like `url`:

1. JVM system property (`-Durl=...`)
2. Environment-scoped key from `env` (`qa.url`, `uat.url`, `QAurl`, `UATurl`)
3. Provided default value in code

## Test Data (CSV)

Login tests read credentials from the CSV file below:

- `src/test/resources/testdata/login-credentials.csv`

Expected columns:

- `username`
- `password`

CSV loading is implemented in `tests.CsvUtils` and consumed by `tests.LoginTest`.

## Test Groups

Run by TestNG group:

```bash
mvn test -Dgroups=smoke
mvn test -Dgroups=regression
mvn test "-Dgroups=smoke,regression"

# Rest Assured tests only
mvn test "-Dtest=tests.RestAssuredApiTest"
mvn test "-Dtest=tests.RestAssuredApiTest" "-Dgroups=smoke"
mvn test "-Dtest=tests.RestAssuredApiTest" "-Dgroups=regression"

# Login tests only
mvn test "-Dtest=tests.LoginTest"
```

## Logger File Details

`LoggerUtil` writes logs to this file path:

- `target/logs/framework.log`

Log directory is created automatically at runtime.

## Extent Report And Screenshots

Extent report is generated by TestNG listener `tests.listeners.ExtentTestListener`.

Generated artifacts:

- HTML report: `target/extent-reports/extent-report-<timestamp>.html`
- Screenshots folder: `target/extent-reports/screenshots/`

Screenshot behavior:

- Pass: screenshot attached to test node
- Fail: screenshot attached to test node

Suite files with listener registration:

- `testng.xml`
- `testng-smoke.xml`
- `testng-regression.xml`
